# Data Architect

_design · task T3 · run RUN-9C44C548 · model `anthropic/claude-opus-5+claude-sonnet-5+claude-haiku-4-5-20251001`_

## What this role decided

I set the data ownership, physical model detail, retention and lineage rules that the settled architecture assumed but never stated. The load-bearing ones: (1) there is no local user entity and there never will be — the workforce IdP is the system of record for identity, and `links` carries a composite `owner_subject` of `iss|sub` (not bare `sub`, which is only unique within an issuer) with no foreign key and therefore no cascade, which is exactly why offboarding needs an explicit rule rather than a delete; (2) deletion is soft, and purge redacts `target_url` and `owner_subject` while keeping the `code` row forever, so a short code can never be re-issued to a different destination — code reuse is a redirect-hijack primitive on confidential data, and the UNIQUE index must therefore span deleted rows while the list index is partial on `deleted_at IS NULL`; (3) retention is now a decision, not a default: links soft-deleted rows purge at +30 days, sessions purge 24h past absolute expiry, OIDC state rows TTL 10 minutes, audit_events retained 400 days on monthly partitions dropped whole; the honest caveat is that RDS PITR (7d) and snapshots (30d) extend the effective life of a deleted URL to 30 days, and I have written that down rather than let anyone claim erasure is immediate; (4) `clicks` is a stored aggregate with no underlying event rows because SEC-7 forbids per-visit records — I am classifying it as a non-authoritative operational metric that must never be used for billing, chargeback or evidence, because it is unreconcilable by construction; (5) Alembic is the sole system of record for physical schema — no `create_all` anywhere including tests, migrations run as a pre-rollout job, expand/contract only, backward-compatible for one release. Residency is single-region with no cross-region replication of any kind, backups included. The one thing I cannot decide alone is what happens to a leaver's links; that is a missing business rule and I have flagged it as blocking the retention job, not the build.

## Decisions

- DATA-1 System of record, one line per entity. Identity (subject, email, display name, group membership): the workforce OIDC IdP — authoritative, never copied into application tables. Session state: the `sessions` table — authoritative but derived and disposable; losing it logs everyone out and loses nothing else. Short link mapping (code → target_url, owner, created_at): the `links` table — the only authoritative business data in the system, and the only thing that must survive a rebuild. Security-relevant actions: the `audit_events` table — authoritative and non-reproducible. Physical schema: Alembic revisions in apps/api. External data shape: contracts/openapi.yaml. Derived click totals: nothing is the system of record; see DATA-9.
- DATA-2 Identity is referenced, never replicated. `links.owner_subject` is TEXT NOT NULL holding a composite `iss|sub` (issuer URL, pipe, subject), computed once at session establishment and stored server-side in `sessions`. No email address, display name, department or group is ever persisted in `links`, `audit_events` or any application table; the UI resolves display identity from the current session's ID-token claims at render time. Consequence: an IdP-side name or email change requires no migration here, and a subject-access request against this system returns a pseudonymous identifier plus the URLs that identifier created, nothing more.
- DATA-3 `links` physical model. `id` BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY (surrogate, never exposed); `code` VARCHAR(7) NOT NULL with an explicit case-sensitive collation (C or the database default binary collation — citext and any *_ci collation are prohibited, see DATA-4); `target_url` TEXT NOT NULL CHECK (char_length(target_url) BETWEEN 1 AND 2048); `owner_subject` TEXT NOT NULL; `clicks` BIGINT NOT NULL DEFAULT 0 CHECK (clicks >= 0); `created_at` TIMESTAMPTZ NOT NULL DEFAULT now(); `deleted_at` TIMESTAMPTZ NULL; `purged_at` TIMESTAMPTZ NULL. All timestamps are TIMESTAMPTZ stored in UTC — no naive timestamps anywhere in the schema. The table is in 3NF: every non-key column depends on the surrogate key alone, with the single deliberate exception recorded in DATA-9.
- DATA-4 Index set, derived from the three queries the application actually issues. (a) `links_code_key` UNIQUE btree on `code`, covering every row including soft-deleted and purged ones — this index is what makes code reuse impossible, so it must never be made partial. (b) Partial composite btree on `(owner_subject, created_at DESC) WHERE deleted_at IS NULL` — serves the one list query (`my links, newest first`) as an index-only ordered scan and keeps deleted rows out of the hot index. (c) Partial btree on `(deleted_at) WHERE deleted_at IS NOT NULL AND purged_at IS NULL` — serves the purge sweeper so it never scans the whole table. No index on `target_url` (never a predicate) and none on `clicks` (never ordered by, at this size). No other index is approved; each one is a write tax on the redirect path, which is a write path (ADR-4).
- DATA-5 Code retirement, and why deletion is soft. Delete sets `deleted_at`; the redirect statement becomes `UPDATE links SET clicks = clicks + 1 WHERE code = :code AND deleted_at IS NULL RETURNING target_url`, so a deleted link 404s immediately. At `deleted_at + 30 days` a purge job sets `target_url = ''`, `owner_subject = ''` and `purged_at = now()`, but the row and its `code` are retained permanently as a tombstone. A short code is therefore never re-issued. Cost: the table never shrinks — approximately 100 bytes per retired code, which at internal team volume is irrelevant, and I would rather pay it than accept a redirect-hijack window.
- DATA-6 Retention schedule, per entity, enforced by a scheduled job and not by hope. `links` (live): retained until the owner deletes it or offboarding policy fires (DATA-11) — no automatic expiry of active links. `links` (soft-deleted): purged per DATA-5 at +30 days. `links` (tombstone): permanent. `sessions`: deleted 24 hours after absolute expiry (SEC-2 gives 8h absolute, so max row life ~32h); the sweeper runs hourly. OIDC pre-session `state` records: TTL 10 minutes, deleted on use, sweeper deletes stragglers. `audit_events`: 400 days, then the whole month partition is dropped (DATA-8). Every one of these is a decision with a named owner (Data Architect) and can be changed only by a new decision, not by editing a config default.
- DATA-7 Residency and encryption at rest. All data lives in exactly one AWS region — the region hosting the ALB and RDS instance. No cross-region read replica, no cross-region snapshot copy, no cross-region backup vault, no global table. RDS storage, snapshots and PITR are encrypted with a customer-managed KMS key with annual rotation enabled. I explicitly rejected column-level encryption of `target_url`: the application needs plaintext on every single redirect, so the key would be resident in the application process anyway and the only real gain would be against a stolen snapshot — which the CMK already covers. Stated cost and honest caveat: PITR (7 days) plus snapshot retention (30 days) means a purged URL remains recoverable from backup for up to 30 days after purge. Erasure is therefore 'removed from live systems immediately, from all copies within 60 days of user deletion'. Nobody may claim faster.
- DATA-8 `audit_events` is append-only by grant, not by convention. The table is declared PARTITION BY RANGE (occurred_at) with monthly partitions created a quarter ahead; retention is executed as DROP PARTITION, which is O(1) and leaves no bloat. The application database role is granted INSERT and SELECT only — no UPDATE, no DELETE, no TRUNCATE on this table. Retention runs as a separate migration/maintenance role. Columns: `event_type`, `actor_subject` (composite iss|sub, nullable for failed logins where the subject is unknown), `link_code`, `ip` (inet), `occurred_at` (timestamptz, partition key). `ip` is personal data and is retained in full for 400 days because a truncated address is useless for the investigation the log exists to support; the retention bound is the control, not truncation.
- DATA-9 `clicks` is classified as a non-authoritative operational metric. Because SEC-7 forbids per-visit rows, there is no event stream from which the counter can be recomputed, reconciled or corrected. It is therefore accurate-by-construction under normal operation and unrecoverable after any anomaly. It must not be used for billing, chargeback, SLA evidence, security investigation or any decision with a consequence; it exists to satisfy AC-3 and to give a user a rough sense of use. If anyone later needs defensible click data, that is a new entity (`click_events`, partitioned, with its own retention and a PII decision) and a new decision from this role — not a reinterpretation of this integer.
- DATA-10 Consistency and transaction boundaries. The transactional boundary is a single `links` row; there is no multi-row invariant in this system and therefore no need for anything above READ COMMITTED. Specifically: (a) the redirect increment is its own single-statement transaction, committed before the 307 (ADR-4); (b) the audit row for link-created and link-deleted is written in the SAME transaction as the `links` mutation, so the audit trail can never disagree with the data — a failed audit insert fails the mutation; (c) login/logout audit rows have no business row to bind to and commit independently; (d) the list view is eventually consistent with concurrent clicks by milliseconds, and that is accepted — AC-3's assertion belongs at the repository/DB level, not against a rendered page. Read replicas are prohibited from serving GET /links: the create-then-list and click-then-list flows would read stale rows and make AC-1 and AC-3 appear intermittently broken. Single writer, single reader, one instance.
- DATA-11 Offboarding is a data-lifecycle rule and it is currently missing. Until the client answers (see open questions), the implemented default is: links owned by a subject the IdP no longer recognises remain in the database and continue to resolve, and a monthly reconciliation report lists them for a human decision. I am deliberately NOT auto-deleting them (silently breaking links other teams depend on) and NOT auto-transferring them (assigning one person's confidential URLs to another without consent). The reconciliation query is `SELECT owner_subject, count(*) FROM links WHERE deleted_at IS NULL GROUP BY 1` cross-checked against the IdP; it does not need a new external service because it is a report, not an integration.
- DATA-12 Migration safety. Alembic is the only mechanism permitted to issue DDL in any environment, including tests — `Base.metadata.create_all` is prohibited even in fixtures, so the test suite exercises the same schema the production migration produces. Migrations are forward-only and append-only: no revision is ever edited after merge, no `downgrade` is relied on operationally (downgrade bodies may exist but are not a rollback strategy). Every change is expand/contract and remains backward-compatible with the previously deployed application for one full release: add nullable or defaulted columns first, backfill in a separate batched revision, tighten constraints in a third, drop only after the code that used the column has been out of production for a release. New columns on `links` must be added with a DEFAULT and NOT NULL applied only after backfill (Postgres 12+ makes the default itself cheap, but the backfill is not). Migrations run as a dedicated pre-rollout Kubernetes job with a single replica, never on application startup — multiple pods racing Alembic on boot is how a migration lock becomes an outage.
- DATA-13 Field-level lineage, recorded so it is reviewable. `links.owner_subject` ← session ← ID token `iss` + `sub` claims ← workforce IdP (upstream SoR; this system holds a pseudonymous copy only). `links.target_url` ← user paste → normalised by `domain/url_policy.py` (fragment stripped, host lowercased) → stored; the stored value is the normalised form, not the raw paste, and the raw paste is retained nowhere. `links.code` ← `secrets.choice` at creation, no upstream, no derivation from the URL (so it leaks nothing about the target). `links.clicks` ← the redirect path only, incremented in place, no upstream and no history. `audit_events.actor_subject` ← same session lineage as owner_subject. Nothing in this system feeds any downstream system; there is no export, no analytics sink and no replication, and adding one is a change to this decision.
- DATA-14 URL credential handling. `domain/url_policy.py` must additionally reject targets containing a userinfo component (`https://user:pass@host/...`) at creation time, because that is a credential the system would otherwise store in plaintext and hand to a browser. Query strings are accepted (they are routinely load-bearing) and the whole `target_url` value is classified confidential in consequence: never logged (SEC-8 already enforces this), never included in error messages, never emitted in metrics labels or trace attributes, and never used as a cache key anywhere.
- DATA-15 `sessions` stores SHA-256(token), not the token. The primary key is the digest of the opaque 256-bit cookie value; lookup hashes the presented cookie and matches. A snapshot, backup or accidental SELECT of the sessions table therefore yields no usable credential. Columns: `token_sha256` (bytea PK), `subject` (iss|sub), `issued_at`, `absolute_expires_at`, `last_seen_at`, `idp_sid`, all TIMESTAMPTZ. Index: btree on `absolute_expires_at` for the sweeper. `last_seen_at` write coalescing (SEC-2, at most once per minute) is what keeps this table off the hot write path.

## Findings

- The spec classifies the data confidential but states no retention period for any entity. Four tables (links, sessions, audit_events, oidc auth state) would otherwise grow forever, which turns a small internal tool into an indefinitely accumulating store of confidential internal URLs.
- `owner_subject` was specified as the OIDC `sub`. A `sub` is only guaranteed unique within an issuer; if the tenant is ever re-pointed at a second IdP or a new tenant, two distinct humans can collide on one subject value and one user inherits another's links. This is a silent authorisation failure, not a visible bug.
- Nothing in the settled decisions says what happens when a link is deleted. If a row is hard-deleted, its 7-char code returns to the free pool and a future CSPRNG draw can re-issue it — anyone still holding the old link in a chat thread would then be redirected to a colleague's unrelated confidential URL.
- There is no local user table, therefore no foreign key from `links.owner_subject` and no referential integrity or cascade. Orphan detection after an employee leaves cannot be a database concern; it has to be a reconciliation job against the IdP, and that job needs a business rule that does not currently exist.
- `clicks` is a derived aggregate stored on the aggregate root with no source events (SEC-7 deliberately forbids per-visit rows). That is a legitimate denormalisation, but it means the number can never be recomputed, audited or corrected after a rollback or a partial failure. It must be labelled as a metric, not a record.
- The short code is case-sensitive base62. If the column is ever created as `citext` or under a case-insensitive collation, the keyspace silently collapses from 62^7 to 36^7 and distinct codes start colliding. This is an unstated correctness dependency of ADR-3.
- RDS point-in-time recovery and snapshots quietly extend the retention of any purged URL. Any claim that a deleted link is gone is false until the backup window has also passed; this needs to be stated rather than discovered during an incident.
- The session cookie value was specified as an opaque 256-bit identifier with server-side state. If the identifier itself is stored in the `sessions` table, a single read of that table (backup, snapshot, support query) yields live, usable sessions.
- `audit_events` is described as append-only but nothing enforces it. Append-only is a grant decision, not an adjective.
- No entity in the model has a stated system of record. Identity, session state, link mappings and audit facts have four different owners with different retention and different erasure obligations, and conflating them is how retention jobs delete the wrong thing.

## Open questions

- BLOCKING THE RETENTION JOB, NOT THE BUILD — what happens to a leaver's links? Three options with different data consequences: (a) links keep resolving indefinitely and appear in nobody's list (chosen as the interim default in DATA-11, safest for consumers, worst for accountability); (b) links are transferred to a named team owner on offboarding (needs a designated owner and a legal basis for reassigning one person's confidential URLs); (c) links are disabled N days after the subject is deprovisioned (needs N, and will break links other teams are relying on). This is a business rule the client must state; I will not invent it.
- Confirm the single AWS region for DATA-7. If any part of the workforce is subject to a jurisdiction that constrains where internal URLs (which can embed customer identifiers in query strings) may be stored, the region choice stops being an infrastructure preference and becomes a residency obligation.
- Is a link ever expected to expire on its own? The current model retains active links forever, which is correct for a bookmark-style tool and wrong for a share-a-draft tool. If the client wants per-link expiry, it is one nullable `expires_at` column plus a predicate in the resolve statement — cheap now, an expand/contract migration later.
- Should the 400-day audit retention be shorter? I chose it to cover an annual review plus one cycle. If the security or compliance function has a stated log-retention standard, that standard wins over my default and I will re-cut the partition retention.
- Confirm nobody downstream wants a click export. DATA-9 makes `clicks` explicitly non-authoritative; if anyone is already planning to report on it, that expectation needs to be corrected now rather than after the first number is questioned.
