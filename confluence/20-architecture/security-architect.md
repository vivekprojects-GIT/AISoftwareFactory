# Security Architect

_design · task T2 · run RUN-9C44C548 · model `anthropic/claude-opus-5+claude-sonnet-5+claude-haiku-4-5-20251001`_

## What this role decided

I set the security posture for the shortener on top of the settled architecture, and my contribution is the parts nobody else has fixed: the exact OIDC/session security envelope behind the BFF decision (PKCE S256, state+nonce, JWKS validation, cookie crypto, 8h absolute / 30m idle lifetime, rotation on login, server-side revocation on logout), the CSRF control that SameSite=Lax alone does not give for POST /links (Origin/Sec-Fetch-Site check, enforced server-side), and the return-to open-redirect hole that the login bounce on /r/{code} opens if left unvalidated. I ran STRIDE across the four trust boundaries (browser→ALB, ALB→pod, pod→Postgres, pod→IdP/Secrets Manager) and the finding that matters most is a data-protection one the acceptance criteria hide: target_url is user-pasted and at this classification will contain access tokens, signed S3 links and document IDs in query strings, so it is secret-bearing free text — it must never appear in application logs, error responses, traces or CI fixtures, and it is encrypted at rest under a customer-managed KMS key with the column treated as confidential. On authorisation I split the model explicitly: /links list and delete are owner-only, enforced by owner_subject predicate in the repository layer (never a client-side filter); /r/{code} is any-authenticated-workforce, which is the deliberate, named consequence of making short links shareable inside the team. On PII I decided the click counter stays a bare integer with no viewer identity, timestamp or IP attached, which keeps this tool out of employee-monitoring territory by design rather than by policy. Secrets (OIDC client secret, session signing key, DB credentials) come from AWS Secrets Manager via IRSA at runtime — never a build arg, image layer, env file or repo. Two items need a human: whether workforce-wide resolution of any colleague's short link is acceptable to the data owner, and the leaver/retention rule for links owned by a departed employee.

## Decisions

- SEC-1 Session token format: the session cookie carries an opaque 256-bit CSPRNG identifier; all session state (sub, email, issued_at, last_seen, idp_sid) lives server-side in a `sessions` table in the same Postgres instance. Attributes: `__Host-` prefix, HttpOnly, Secure, SameSite=Lax, Path=/, no Domain. Rationale: opaque + server-side gives true logout/revocation, which a self-contained token cannot; it keeps the OIDC `sub` out of the client entirely; and it reuses the approved database rather than introducing Redis or any new capability. Cost: one indexed session lookup per request.
- SEC-2 Session lifetime: 8 hours absolute, 30 minutes idle (last_seen refreshed at most once per minute to bound write load), session id regenerated on successful login (fixation defence) and deleted server-side on logout. Back-channel logout from the IdP, if the IdP supports it, deletes sessions matching idp_sid; otherwise the 8h absolute cap is the containment bound for a revoked employee.
- SEC-3 OIDC flow hardening, all server-side in /auth/callback and all mandatory: authorization code + PKCE with code_challenge_method=S256 only; single-use `state` bound to a pre-session cookie and compared with constant-time equality; `nonce` generated per attempt and required to match the id_token claim; id_token signature verified against the IdP JWKS (cached with TTL, refetched on unknown kid, RS256/ES256 allowlist — `alg: none` and HMAC algorithms rejected); iss, aud==client_id, exp/iat/nbf checked with <=60s skew; authorization code exchanged exactly once. Access/refresh tokens from the IdP are not stored — this application needs no downstream API call on the user's behalf, so it takes the identity claims and discards the tokens.
- SEC-4 CSRF: SameSite=Lax stops cross-site POST cookie attachment, but it is a browser-version-dependent control and does not cover same-site subdomain attackers. Every state-changing request (POST /links, DELETE /links/{id}, POST /auth/logout) additionally requires `Origin` (fallback `Referer`) to match the configured application origin exactly, rejected with 403 when absent or mismatched, enforced in one FastAPI dependency applied to all non-safe methods. GET /r/{code} is deliberately exempt — it is a safe navigation and must remain reachable from mail and chat clients.
- SEC-5 Login return-to: the post-login redirect target is stored server-side against the pre-session `state` record, never taken from a query parameter reflected back into the Location header. It is additionally validated as a same-origin path starting with a single `/` (rejecting `//host`, `/\host`, backslash and encoded variants). This closes the open redirect that authenticating /r/{code} would otherwise create.
- SEC-6 Authorisation model, enforced server-side at the repository layer: (a) POST /links — any authenticated workforce user; owner_subject is taken from the session, never from the request body; (b) GET /links and DELETE /links/{id} — owner-only, implemented as a mandatory `owner_subject = :session_sub` predicate inside the repository methods so no caller can construct an unfiltered query; (c) GET /r/{code} — any authenticated workforce user, deliberately not owner-scoped, because a short link nobody else can open is not a short link. Evidence: a two-user negative test asserting user B receives 404 (not 403) for user A's link id, and that user B's list never contains user A's rows. 404-not-403 avoids confirming existence.
- SEC-7 PII and telemetry minimisation: the click counter stays a bare monotonic integer. No viewer subject, IP, user-agent or timestamp is stored per visit, and the `links` table gains no such columns. This is a deliberate design-level guarantee that the tool cannot be repurposed as employee activity monitoring, and it removes the need for a DPIA. Consequence accepted: 'who clicked my link' and per-day click history are permanently unavailable without a new, separately-approved design decision.
- SEC-8 Log redaction as an enforced control, not a guideline: a logging filter in apps/api strips any value matching a URL pattern down to `scheme://host/<redacted>` before emission, and the `Link` response/domain model overrides its repr/str so `target_url` cannot reach a log or traceback through an f-string or exception message. Structured log fields are limited to: request id, route, status, latency, session sub, link code. Never logged: full target_url with query or fragment, session cookie value, id_token, OIDC client secret, Authorization headers. Unit test: constructing a Link with a token-bearing URL and formatting it must not emit the token.
- SEC-9 Audit log: an append-only `audit_events` table (event_type, actor_subject, link_code, ip, occurred_at) records login success/failure, logout, link created, link deleted. It does not record redirect resolutions with actor identity — that would reintroduce the monitoring surface SEC-7 removes; redirect volume is observable in aggregate only. Retention 180 days, then hard delete via a scheduled job.
- SEC-10 Encryption in transit: TLS 1.2 minimum with TLS 1.3 preferred at the ALB (ACM certificate, modern security policy, HTTP redirected to HTTPS at the listener). HSTS `max-age=31536000; includeSubDomains` on all responses. Pod→Postgres uses `sslmode=verify-full` with the RDS CA bundle mounted into the image — `require` is explicitly insufficient because it verifies nothing. Pod→IdP and pod→Secrets Manager are TLS with default trust store verification, no certificate pinning. Residual risk accepted and named: the ALB→pod hop is plaintext HTTP inside private subnets, restricted by security group to the ALB security group only; revisit if classification rises above confidential or if a service mesh is adopted.
- SEC-11 Encryption at rest and key ownership: RDS PostgreSQL encrypted with a customer-managed KMS key owned by the platform team (not the AWS-managed default), automatic annual key rotation enabled, automated backups and snapshots inheriting the same key, `deletion_protection = true`, and the instance in private subnets with no public accessibility. CloudWatch log groups encrypted with the same CMK. Key policy grants the application role `kms:Decrypt` only, via the RDS service principal condition; only the platform role holds `kms:ScheduleKeyDeletion`.
- SEC-12 Secrets management: three runtime secrets — OIDC client secret, session/state signing key, and DB credentials — all live in AWS Secrets Manager and are resolved at pod start via IRSA (External Secrets Operator or SDK fetch on boot). Prohibited and CI-enforced: secrets in the repository, in Dockerfile ARG/ENV, in image layers, in Kubernetes manifests committed to git, or in GitHub Actions repository secrets used at build time. GitHub Actions authenticates to AWS via OIDC role assumption, not long-lived access keys. Rotation: DB credentials rotated by Secrets Manager managed rotation on a 90-day schedule; OIDC client secret rotated annually or on suspicion, using the IdP's dual-secret overlap window; session signing key carries a `kid` with a two-key verify/one-key sign window so rotation is zero-downtime. A gitleaks/secret-scan step blocks the pipeline on detection.
- SEC-13 Least privilege, written down: (a) the application DB role holds SELECT/INSERT/UPDATE on `links`, SELECT/INSERT/UPDATE/DELETE on `sessions`, INSERT/SELECT on `audit_events`, and no DDL, no SUPERUSER, no CREATE; migrations run as a separate `migrator` role from a Kubernetes Job, never from the API process. (b) The API pod's IAM role permits only `secretsmanager:GetSecretValue` on the three named secret ARNs plus `kms:Decrypt` on the one CMK — no wildcards. (c) Containers run as non-root with a read-only root filesystem, `allowPrivilegeEscalation: false`, all capabilities dropped. (d) A default-deny NetworkPolicy permits egress only to the Postgres port, the IdP, and the AWS endpoints — this, not just url_policy, is the second layer that stops the service being used to probe internal networks.
- SEC-14 Browser-facing response headers on every response: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` (already settled for the redirect — I extend it to all routes), `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'self'; form-action 'self' <idp-origin>`, `Permissions-Policy` denying camera/microphone/geolocation. CORS is not enabled: the SPA is served same-origin behind the same ALB, so any need for a wildcard or credentialed cross-origin policy is a design regression to be raised rather than configured.
- SEC-15 Abuse controls on the redirect path: per-session rate limit of 60 resolutions/minute and 20 creations/minute, enforced in the API with a fixed-window counter in Postgres (no new capability), returning 429 with Retry-After. Unknown-code responses return a constant-shape 404 body. This bounds both the enumeration residual and the single-row write contention from ADR-4.
- SEC-16 Compliance posture stated for the record: internal workforce tool, no customer data, no payment data, no special-category data — so PCI-DSS and HIPAA do not apply and no regulator notification regime attaches. GDPR/UK GDPR does apply to `owner_subject` and `audit_events.actor_subject`; lawful basis is legitimate interest (operating an internal tool), the processing record is one line in the existing internal ROPA, no international transfer occurs beyond the chosen AWS region, and the subject-access/erasure answer is 'delete the user's links and audit rows by owner_subject' — a single query, kept feasible by SEC-7's minimisation.

## Findings

- S (Spoofing) — browser→ALB boundary: the OIDC code exchange is only as strong as its parameter validation. Without a per-attempt `state` bound to the session, a `nonce` echoed in the id_token, PKCE S256 (not `plain`), and full id_token validation (signature against cached JWKS, iss, aud == client_id, exp/iat with <=60s skew), the BFF callback is a login-CSRF and token-injection surface. The settled decision names PKCE but not these checks; they are load-bearing and must be implemented, not assumed to be in the library.
- T (Tampering) — session cookie: 'signed HttpOnly cookie' is under-specified. A signed-but-readable cookie leaks the OIDC `sub` to anyone with a browser dump or a mis-scoped log. The session must be an opaque server-side reference or an authenticated-encrypted token; a plain HMAC of a JSON payload is not sufficient at confidential classification.
- R (Repudiation) — there is no audit trail in the settled design. Link creation, deletion and authentication events are exactly the actions a security investigation would need after an internal phishing report ('someone shortened a credential-harvesting URL'). Without an append-only auth/creation log this is unreconstructable.
- I (Information disclosure) — HIGHEST RISK, and it is invisible in the acceptance criteria: `target_url` is arbitrary user-pasted free text. In practice internal users will paste pre-signed S3 URLs, Confluence/Jira links with tokens, Grafana share links and `?access_token=` query strings. That column is secret-bearing. Any code path that logs the URL, echoes it in a 4xx/5xx body, puts it in an exception message, or ships it to an APM trace is a credential leak. The 307 `Location` header itself is fine (TLS), but `Referrer-Policy: no-referrer` (already settled) is what stops it leaking onward to the destination site.
- I — open redirect, second instance: the settled design authenticates GET /r/{code}, so an unauthenticated visit must bounce to /auth/login with a return-to. If that return-to is echoed into the post-login redirect without validation, the login endpoint becomes an open redirect on a trusted internal hostname — precisely the primitive the url_policy domain function exists to deny on the other route.
- I — enumeration residual: 7-char CSPRNG base62 defeats guessing statistically, but there is no rate limit, so a compromised workforce session can still scan and a 404-vs-200 timing difference is measurable. Volume control belongs at the edge, not in the domain layer.
- E (Elevation) — the ownership rule ('their list') exists only as an index on (owner_subject, created_at). An index is not authorisation. If any query in the list or delete path omits the `owner_subject = :session_sub` predicate, every user reads every colleague's confidential URLs and the tests still pass because the fixtures have one user. This must be a repository-layer invariant with a multi-user negative test, not a service-layer convention.
- D (Denial of service) — ADR-4 makes every redirect a write to one row; a single hot link serialises, and an authenticated user can trivially amplify that. Accepted at team scale, but it means the redirect path must be rate-limited per session and the DB connection pool bounded so redirect load cannot starve the create path.
- Boundary gap — pod→Postgres: nothing in the settled decisions requires TLS to the database or certificate verification. `sslmode=require` without `verify-full` accepts any certificate and does not protect against an in-VPC MITM.
- Compliance — `owner_subject` (OIDC sub) is personal data under GDPR/UK GDPR even though it is pseudonymous, because the IdP can re-identify it. Link ownership plus a click counter is a lawful, low-risk internal processing activity — but only while no per-visit viewer identity is stored. If per-click viewer logging is ever added, this becomes employee activity monitoring and needs a DPIA and, in EU jurisdictions, works-council consultation.
- Supply chain / secrets — the settled deploy story (Kubernetes on AWS, GitHub Actions) has no stated secret path. The default failure mode at this size is an OIDC client secret in a GitHub Actions repo secret baked into the image as a build arg, where it persists in every layer and in the registry.

## Open questions

- SEC-6(c) needs the data owner's confirmation: any authenticated colleague can resolve any short code, so a link to a restricted HR or finance document becomes readable by the whole workforce via its code. The alternative — owner-only resolution — makes the product useless. I recommend keeping team-wide resolution and adding a visible warning at creation ('anyone in the company with this link can open it'), but this is a confidentiality decision for a human, not for me.
- Leaver policy: when an employee offboards, what happens to their links? Options are (a) retain and reassign ownership to a team account, (b) retain but orphan (list becomes unreachable, redirects keep working), (c) delete, breaking every published short link. I have not chosen; the schema supports all three. Needs an owner decision before the first offboarding, not after.
- Retention for `links` itself: no expiry is currently specified, so a shortener at confidential classification accumulates pre-signed URLs and token-bearing links indefinitely. I recommend an optional per-link expiry plus automatic deletion of links unclicked for 24 months. Confirm whether that is acceptable to the product owner.
- Which OIDC IdP, and does it support back-channel logout (SEC-2) and dual client secrets during rotation (SEC-12)? If neither, the 8h absolute session cap becomes the only revocation bound for a terminated employee and the client-secret rotation requires a brief maintenance window — both acceptable, but the platform team should know.
- Is the ALB internal-only (private, reachable via VPN/zero-trust proxy) or internet-facing with the OIDC login as the sole gate? Internal-only removes the unauthenticated internet from the threat model entirely and I would recommend it; internet-facing means SEC-15's rate limiting and WAF rate rules on /auth/* become the primary defence against credential-stuffing noise.
