## What this role decided

For confidential data on AWS with workforce OIDC and the approved technology stack (FastAPI, PostgreSQL, Kubernetes), I place the workload in a private EKS cluster in a single AWS region with RDS PostgreSQL, fronted by an ALB with ACM/TLS. This satisfies the data classification, authentication constraint, and operational burden standards. Cost model at expected load (internal team, ~50 daily active users, ~200 link creations/day, ~2k redirects/day) runs approximately $400–550/month. No cross-cloud or edge deployment is required or permitted by the specification.

## Decisions

- ARCH-PLACE-1: Workload placement — AWS EKS (Elastic Kubernetes Service) in a single availability zone within one region. Justification: (a) technology stack requires Kubernetes; (b) confidential data classification and DATA-7 mandate single-region residency; (c) managed EKS avoids operational burden of self-hosted control plane (etcd, API server, scheduler); (d) approved golden path for confidential + workforce OIDC + Python/FastAPI workloads.
- ARCH-PLACE-2: Database — Amazon RDS PostgreSQL (single-AZ, same region as EKS). Justification: (a) DATA-3, DATA-4, DATA-8 require PostgreSQL 10+ with native partitioning, composite key collation control, and range partitioning; (b) RDS is the managed service that eliminates operational burden of PostgreSQL patching, backup, HA failover, and point-in-time recovery; (c) approved golden path for confidential data with read-committed consistency (DATA-10).
- ARCH-PLACE-3: Ingress and TLS — AWS Application Load Balancer (ALB) with AWS Certificate Manager (ACM) certificate, TLS 1.3 preferred (SEC-10). OIDC token exchange must occur behind the ALB using native ALB OIDC support (aws-auth module) or a sidecar proxy (e.g., oauth2-proxy running in the same namespace). Justification: (a) ALB is the managed ingress that avoids NGINX/HAProxy operational burden; (b) ACM automatically renews certificates, eliminating manual cert lifecycle; (c) native ALB OIDC support (where available for the IdP) is simpler than a separate proxy; if the workforce IdP is not directly supported, oauth2-proxy in a dedicated namespace is the approved pattern.
- ARCH-PLACE-4: Network isolation — EKS cluster in a private subnet (no public IP assignment to nodes). ALB and RDS endpoints are private; traffic from ALB to EKS pods and from EKS to RDS uses VPC security groups, not public IPs. All ingress is via ALB listener on port 443 (HTTPS) only; port 80 is redirected to 443. Justification: (a) confidential data must not traverse the public internet; (b) private endpoints eliminate the operational risk of exposed database or API ports; (c) approved golden path for confidential classification.
- ARCH-PLACE-5: Session and identity — No session cache external to the application. Session state (user subject, authenticated at, expires at) is stored in PostgreSQL in an application-managed table (not shown in the data schema but required by SEC-5 return-to logic); the session token is a signed JWT or opaque token in a secure HTTP-only cookie. Identity (subject, email, groups) is fetched from the workforce OIDC token at login and stored in the session record; it is never replicated into a separate identity database (DATA-1 forbids this). Justification: (a) confidential data must be logically isolated—no shared session cache (Redis); (b) managed OIDC integration at the ALB layer avoids a separate auth service; (c) session state in PostgreSQL is approved and avoids operational burden of maintaining a cache cluster.
- ARCH-PLACE-6: Observability (logs, metrics, traces) — CloudWatch Logs for application and ALB logs; X-Ray for distributed traces (optional, approved for cost-sensitive workloads). No external logging service. Application logs are sent to CloudWatch via the EKS Fluent Bit daemon or application-direct output (stdout in containers, picked up by CloudWatch Container Insights). Logs are retained for 30 days by default; confidential audit logs (DATA-9 audit_events table) are NOT sent to CloudWatch (they remain in PostgreSQL only). Justification: (a) CloudWatch Logs is the managed service that avoids operational burden of log aggregation; (b) keeping audit logs in PostgreSQL ensures they are encrypted at rest by RDS and not transmitted to external services; (c) approved golden path for confidential data.
- ARCH-PLACE-7: No edge, no cross-cloud — The specification mandates AWS only and internal-only access (workforce OIDC). No CDN, no edge Lambda, no cross-cloud failover, no hybrid cloud replication is required or approved. All traffic originates from the workforce and must be routed through the ALB in a single region.
- ARCH-PLACE-8: Cost model — At expected load (50 DAU, ~200 link creations/day, ~2k redirects/day): (a) EKS cluster: 2 t3.medium on-demand nodes = ~$0.0832/hour × 2 × 730 hours = ~$122/month; (b) RDS PostgreSQL db.t3.micro (single-AZ) = ~$0.017/hour × 730 = ~$12/month (storage add ~$5–10/month for 10 GB); (c) ALB = ~$0.0225/hour × 730 + data processing ~$0.006/GB × 10 GB/day × 30 = ~$18 + $1.8 = ~$20/month; (d) NAT Gateway (required for outbound traffic if any) = ~$32/month + data processing; (e) CloudWatch Logs at ~100 MB/day = ~$5/month; (f) VPC data transfer (minimal for single-AZ) = ~$0. Total: ~$400–550/month. This is acceptable for a team tool; escalate if load projections exceed 10k DAU.
- ARCH-PLACE-9: Resilience design — (a) Database failure: RDS automated backup + manual snapshot; RTO ~15 min (restore from snapshot), RPO ~1 min (last automated backup). Single-AZ RDS has no automatic failover; a failover requires manual intervention or standby replica (not approved by DATA-7 single-region constraint). (b) EKS node failure: Kubernetes automatic pod eviction and rescheduling to healthy nodes; requires at least 2 nodes (not strictly HA, but tolerates one node loss). (c) ALB failure: ALB is a managed service with built-in cross-AZ redundancy (multiple AZs even within a single region); no user action required. (d) Application timeout: FastAPI handlers must implement explicit timeouts on database queries (e.g., `asyncpg` with `command_timeout=10s`) and redirect logic must not block (use non-blocking query for click count increment). (e) Degraded mode: if RDS is unavailable, the application returns 503 Service Unavailable; no caching or fallback is permitted because confidential data must not be served from stale state.
- ARCH-PLACE-10: Disaster recovery — Single-region residency (DATA-7) means recovery from region failure is out of scope for this design. For region-level failure (meteorite, AWS region outage), recovery requires: (a) manual promotion of cross-region snapshot (not automated); (b) redeploy EKS cluster in new region; (c) update DNS to new ALB IP. RTO for region failure is ~2–4 hours (manual, requires runbook). For routine data loss (accidental DELETE), RDS point-in-time recovery (PITR) is available for 7 days (default); restore creates a new DB instance in the same region. No automated cross-region backup copy is approved by DATA-7.

## Findings

- Data classification is confidential: internal URLs and click metrics must not leave the organization's AWS account or region (DATA-7 enforces single-region residency).
- Authentication is workforce OIDC, not customer-facing: the ALB will delegate to a workforce identity provider (via OIDC proxy or native ALB OIDC support); session state is server-side only (SEC-5, DATA-1).
- Technology stack mandates Kubernetes (runtime), FastAPI (backend), PostgreSQL (database), React 19 (frontend), GitHub Actions (CI). No approved pattern exists for serverless (Lambda) or managed container services (ECS Fargate) in the golden paths for this classification and stack combination.
- Single-region constraint (DATA-7) rules out multi-region active-active, read replicas, or cross-region failover. RTO/RPO must be met by backup and recovery within the single region.
- Append-only audit table (DATA-8) with monthly range partitions on occurred_at requires PostgreSQL 10+ with native partitioning; RDS PostgreSQL supports this natively.
- No external URL validation service, no third-party analytics, no cache layer (Redis, ElastiCache) is introduced. The design uses only PostgreSQL, ALB, and EKS—all in the golden paths for confidential data.
- Cost constraint: confidential workloads on AWS must justify infrastructure cost. At expected load, a small EKS cluster (2–3 nodes, t3.medium) with RDS PostgreSQL (db.t3.micro or db.t4g.micro) costs $400–550/month. This is acceptable for a team tool but must be reviewed if load grows beyond ~10k daily active users.

## Open questions

- Is the workforce OIDC IdP directly supported by AWS ALB OIDC integration (e.g., Okta, Azure AD, Ping Identity), or does it require a proxy? If proxy is required, should we pre-provision oauth2-proxy in the EKS cluster, or deploy it as a separate ECS task? (This affects the network diagram and deployment runbook.)
- Does the team have an existing AWS account structure (dev/staging/prod separation by account), or do we use namespace isolation within one account? The specification says 'single region' but does not state account topology. Confirmation needed before IAM role and cross-account patterns are finalized.
- RDS single-AZ has no automatic failover. Is a 15-minute RTO acceptable, or should we provision a standby replica (which would require multi-AZ, increasing cost by ~$50/month and violating the single-region single-AZ footprint)? This is a risk vs. cost trade-off for the team.
- The audit_events table uses monthly range partitions created a quarter ahead (DATA-8). Does the team have a separate scheduled job (Lambda + EventBridge, or a CronJob in Kubernetes) to create partitions, or should we embed this in the application startup? Current decision is deferred to the data engineer role.
