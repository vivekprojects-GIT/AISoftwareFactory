## What this role decided

I have designed the API surface for the URL shortener as a resource-oriented REST service with three stable resources: Link (creation and retrieval), Redirect (resolution with side effect), and AuditEvent (read-only append-only). Versioning strategy is URI-based (/v1/) to enable future breaking changes without client negotiation. Pagination uses cursor-based offsets with strict limits. Idempotency is enforced at the application layer via code-based deduplication for POST /links (deterministic short codes prevent accidental duplicates; retry safety is implicit). Error taxonomy distinguishes between client error classes (malformed input, missing resource, auth failure, policy violation) and server errors, with stable machine error codes for programmatic handling. The surface is contract-first: the OpenAPI 3.1 schema is the agreement, committed to the repository, and CI enforces drift detection. All mutating operations are safe to retry. Backward compatibility is enforced: within /v1/, only additive changes are permitted; breaking changes move to /v2/.

## Decisions

- API_ARCH-1: Resource model — Three stable resources: (a) Link (POST to create, GET to list, GET by code to retrieve one, DELETE to soft-delete); (b) Redirect (GET /u/{code}, side effect is click count increment); (c) AuditEvent (GET to list filtered by link_code or event_type, read-only append-only). No verbs in the URI. POST /links creates, DELETE /links/{code} marks as deleted, GET /u/{code} resolves and counts.
- API_ARCH-2: Versioning and compatibility — URI-based versioning: /v1/links, /v1/audit, /u/{code}. Within /v1/, only additive changes are permitted (new optional fields, new query parameters, new HTTP status codes not previously returned). Removing or narrowing a field, changing status code semantics, or altering required field names is a /v2/ change. This is enforced by contract review and CI drift checks.
- API_ARCH-3: Pagination — Collection endpoints (GET /v1/links, GET /v1/audit) support offset-based pagination with required parameters `offset` (integer ≥ 0, default 0) and `limit` (integer 1–100, default 20). The response includes `total`, `offset`, `limit`, and `items`. Cursor-based pagination is not used because the dataset is small, the sort order is stable (created_at DESC), and offset pagination is simpler for the internal team use case. This is added to the spec as a query parameter set.
- API_ARCH-4: Idempotency — POST /links is idempotent by means of the short code generation logic: if the same long URL is submitted twice, the same short code is returned (deterministic collision-resistant encoding of the URL, not random UUID). The response is 200 OK on idempotent retry (code already exists, same target_url) or 201 Created on first submission. This is safe to retry without coordination. DELETE /links/{code} is idempotent: deleting a non-existent or already-deleted code returns 404, which is idempotent in the sense that the desired end state (code is absent or deleted) is achieved; the caller does not retry 404.
- API_ARCH-5: Error taxonomy — All error responses include (status_code, error_code, message, details). Error codes are stable machine identifiers: INVALID_URL (422), URL_POLICY_VIOLATION (422), LINK_NOT_FOUND (404), UNAUTHORIZED (401), FORBIDDEN (403), CONFLICT (409 for code collision under non-deterministic generation, but not applicable here), INTERNAL_ERROR (500), SERVICE_UNAVAILABLE (503). The message is actionable for humans (e.g., 'URL must start with http:// or https://'); details is optional and may contain structured sub-errors (e.g., which URL policy rule failed). No stack traces are sent to clients.
- API_ARCH-6: HTTP contract for redirect — GET /u/{code} returns 307 Temporary Redirect with Location header set to the decoded target_url and Cache-Control: no-store, Referrer-Policy: no-referrer, Vary: Cookie (because soft-deleted links return 404, not redirect). The click count is incremented server-side as an atomic UPDATE before the 307 is issued. 404 if code does not exist or is deleted. 400 if code is malformed (not 7 alphanumeric). This endpoint is not versioned (/u/ not /v1/u/) because the short code namespace is global and immutable.
- API_ARCH-7: Backward compatibility guardrails — The OpenAPI 3.1 schema is committed to contracts/openapi.yaml. CI enforces drift: if the deployed API schema differs from the committed schema (detected by FastAPI introspection), the build fails. Apps/web generates a typed client from the committed schema and hand-writes against it. Contract changes are reviewed in pull request before merge. The schema is the contract; the code must match it.
- API_ARCH-8: Null and omitted fields — Optional fields are represented as null or omitted from the JSON response, not as empty strings or sentinel values. For example, `deleted_at` is omitted if the link is live, present as an ISO 8601 timestamp if deleted. Arrays are never null; an empty list is []. This is enforced in the Pydantic schema with `exclude_none=True` on the response model.
- API_ARCH-9: Link response model — GET /v1/links/{code} or an item in the list returns: code (string, 7 chars), target_url (string, redacted to scheme://host/<redacted> by SEC-8 filter before emission), clicks (integer ≥ 0), created_at (ISO 8601 timestamp), deleted_at (ISO 8601 or null), owner_subject (not exposed; the API assumes the client is the owner, enforced by authorization layer). The `id` surrogate is not exposed.
- API_ARCH-10: AuditEvent response model — GET /v1/audit returns items with: event_type (string: 'link_created', 'link_deleted', 'login_success', 'login_failure', 'logout'), actor_subject (string, composite iss|sub), link_code (string or null if not link-related), ip (string, IP address of the request), occurred_at (ISO 8601 timestamp). The user can only retrieve their own audit events unless they have an operator role (not defined in this spec, but reserved for future use). This is enforced at the repository layer.
- API_ARCH-11: Content-Type and charset — All responses are application/json; UTF-8 charset is assumed. All requests expect application/json body. The API does not support form-encoded or multipart uploads.
- API_ARCH-12: No hypermedia, no HATEOAS — Links between resources are not represented via hypermedia. The client knows the URL structure (e.g., /v1/links/{code}, /u/{code}) and constructs it. This is acceptable for an internal tool with a single-purpose SPA frontend.
- API_ARCH-13: Authentication and authorization — Enforced at the application layer, not expressed in the OpenAPI schema as a requirement. The session cookie (opaque identifier) carries the user's authenticated subject. Unauthenticated requests to /v1/* receive 401 Unauthorized. Authenticated users can only list and delete their own links (owner_subject matches session subject). This is enforced by the repository layer, not the schema.

## Findings

- The project has already committed to contract-first development via OpenAPI 3.1 generation from FastAPI, with CI drift checks. The API surface design must align with this: the schema is the authority, not generated documentation.
- The transactional boundary (DATA-10) is a single row; the resolve-and-count operation is atomic within one UPDATE, so optimistic concurrency (no row locks across application code) is the correct model.
- The redirect operation is a side effect on read (clicks counter increment during resolution). This is not a RESTful GET; the project has already chosen to make it an atomic UPDATE that returns the target URL. The HTTP contract must reflect this: 307 Temporary Redirect with the query parameter decoded from the short code lookup.
- Soft deletion (DATA-5) means the redirect query must filter on `deleted_at IS NULL`. The API must not expose the `id` surrogate or `deleted_at` timestamp to clients; only `code` and derived fields.
- The owner_subject (DATA-2) is stored server-side and never accepted from the request body (SEC-6). The API must enforce this at the authorization layer, not the contract layer.
- Click count (DATA-9) is non-authoritative but monotonic. It is acceptable to expose it in the list view because there is no event stream to reconcile against; the counter is the only source of truth.
- URL policy (URL acceptance policy, already settled) is enforced at creation time as a pure domain function. The API must reject non-http/https URLs, targets matching the internal network pattern, and URLs over 2048 chars with a clear 422 Unprocessable Entity response.
- Session state (SEC-1, SEC-2) lives server-side. The API contract does not expose session internals; authentication is out-of-band (OIDC flow in /auth, session cookie in subsequent requests).
- Audit events (SEC-9, DATA-8) are append-only and partitioned by occurred_at. The API exposes them as read-only to the calling user; the user can only see their own audit events (creator of the link or the system operator, depending on role).
- The API does not support bulk operations, batch updates, or webhooks. The scope is CRUD on links and read-only audit retrieval.

## Open questions

- QUESTION-1: Should the short code be deterministic (derived from the target URL, e.g., SHA-256 truncated and base36-encoded) or probabilistic (random 7-char code from a pool)? The current spec says 'deterministic collision-resistant' (implicit in the idempotency decision), but this is worth confirming with the product owner. Deterministic means the same long URL always maps to the same short code, which is idempotent and simplifies testing; probabilistic requires a unique constraint and retry logic on collision, which is more complex. Current decision: deterministic.
- QUESTION-2: Should the AuditEvent endpoint be available to all authenticated users (they see only their own events) or only to an operator/admin role? The spec does not define roles. Current assumption: all authenticated users can query their own audit events.
- QUESTION-3: Should the API support filtering audit events by date range (occurred_at between X and Y)? Current spec says no; pagination is by offset only. This can be added as an additive change in /v1/ if needed.
- QUESTION-4: Should GET /v1/links support filtering by deleted status (e.g., ?include_deleted=true to show soft-deleted links)? Current assumption: GET /v1/links returns only live links (deleted_at IS NULL); deleted links are visible in the audit log, not in the list.
- QUESTION-5: Should the API support a bulk delete operation (DELETE multiple codes in one request)? Current spec says no; each delete is a single request.
- QUESTION-6: Is the 7-character code length specified elsewhere (e.g., in DATA-3)? Current assumption: yes, DATA-3 says `code` VARCHAR(7). The API contract must enforce this on retrieval (reject requests with code not matching [A-Za-z0-9]{7}).
